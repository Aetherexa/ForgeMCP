# v0.3 Sprint 5 — Lifecycle-Aware Service Disposal

**Status:** complete.

## Sprint goal

Make ForgeMCP deterministically dispose the services it constructs, across startup rollback, execution completion, and application shutdown, without taking ownership of caller-supplied values.

Sprint 4 completed deterministic module composition. Sprint 5 closes the remaining v0.3 lifecycle gap: service factories can create resources, but the runtime does not yet release them.

## User outcome

A developer can:

1. return an object implementing `Symbol.asyncDispose` or `Symbol.dispose` from a service factory;
2. rely on ForgeMCP to dispose application-lifetime factory services when the application shuts down;
3. rely on ForgeMCP to dispose execution-scoped and transient factory services when one execution ends;
4. rely on cleanup during startup rollback;
5. preserve ownership of instances supplied through `provide(token, value)`;
6. stop an application while requests are in flight without application services being disposed underneath those requests;
7. receive deterministic cleanup diagnostics when one or more disposal hooks fail.

## Ownership model

ForgeMCP ownership follows the registration boundary:

| Registration | Lifetime | Owner | Automatic disposal |
| --- | --- | --- | --- |
| `provide(token, value)` | application | caller | no |
| `provideFactory(token, factory)` | application | ForgeMCP | application rollback/stop |
| `provideScopedFactory(token, factory)` | execution | ForgeMCP | execution end |
| `provideTransientFactory(token, factory)` | transient | ForgeMCP | execution end, once per successful construction |

A factory-created result is framework-owned even when it is not disposable. Only results implementing a supported standard disposal symbol require a cleanup call.

Caller-provided values remain caller-owned even if they implement a disposal symbol.

## Disposal protocol

ForgeMCP uses the JavaScript standard disposal protocols only:

1. if an owned service implements `Symbol.asyncDispose`, await it;
2. otherwise, if it implements `Symbol.dispose`, invoke it;
3. otherwise, no cleanup action is required.

If an object implements both protocols, `Symbol.asyncDispose` wins.

This sprint does not infer lifecycle from method names such as `close()`, `destroy()`, `shutdown()`, or `dispose()`.

## Construction and disposal ordering

Successful factory construction records ownership in completion order.

If service A depends on service B:

```text
construct B
construct A

dispose A
dispose B
```

Owned services are disposed in reverse successful-construction order so dependents are released before dependencies.

Every successful transient factory construction is a separate ownership entry.

A factory that throws or rejects before returning a value creates no ownership entry.

## Application-lifetime disposal

Application factory services are owned by the application service runtime.

They are disposed:

- when application service resolution partially succeeds and a later startup service fails;
- when module composition or later startup work fails after services were resolved;
- when a successfully started application stops.

Application factory services are not disposed when an individual execution completes.

Application disposal is idempotent.

## Execution-scope disposal

Each `Application.execute()` call owns one internal disposable service scope.

That scope tracks:

- execution-scoped factory instances;
- every transient factory result constructed during that execution.

The scope is disposed whether middleware/tool execution succeeds or fails.

`ExecutionContext.services` remains a resolver, not a public manual scope-management API.

After the internal scope is disposed, further resolution through a captured resolver fails deterministically rather than constructing new resources outside the execution boundary.

## Graceful application stop

Lifecycle-aware disposal makes active execution tracking necessary.

```text
Started
   |
   | stop()
   v
Stopping
   |
   +--> reject new execute() calls
   +--> wait for already-active execution scopes
   +--> active executions finish and dispose request-owned services
   +--> dispose application-owned services
   v
Stopped
```

Application stop never disposes application services while an already-started execution can still use them.

If an execution never settles, stop may remain pending. Timeouts/cancellation belong to the later resilience milestone rather than this sprint.

## Failure semantics

Disposal is best-effort.

When multiple owned services need cleanup:

- every disposal hook is attempted;
- failures are retained in deterministic reverse-construction order;
- one failure does not skip later cleanup.

The runtime will expose a deterministic service-disposal error containing the affected service identities and underlying errors.

Operation/error interaction:

- successful execution + scope disposal failure → execution rejects with the disposal error;
- failed execution + successful scope disposal → original execution error is preserved;
- failed execution + failed scope disposal → both failures are preserved;
- successful startup work followed by startup failure → owned application services are disposed before the application returns to `Created`;
- startup failure + disposal failure → both failures are preserved;
- application stop + disposal failure → cleanup still attempts every owned service and the application ends in terminal `Stopped` state while `stop()` reports the cleanup error.

A partially disposed application must never return to `Started`.

## Runtime model

```text
ServiceRegistry
     |
     | construct application factories
     | track framework-owned results
     v
ServiceRuntime
     |
     +--> application ownership tracker
     +--> active execution scopes
     |
     +--> createScope()
     |       |
     |       +--> scoped cache
     |       +--> transient constructions
     |       +--> execution ownership tracker
     |       |
     |       +--> dispose at execute() completion
     |
     +--> dispose()
             |
             +--> stop accepting scopes
             +--> await active scopes
             +--> dispose application-owned services
```

## Definition of done

Sprint 5 is complete when factory-created application, execution-scoped, and transient resources are deterministically disposed at their owning lifecycle boundaries, rollback and concurrent shutdown are safe, caller-owned values remain untouched, behavior is proven through the official MCP adapter, and every repository quality gate passes.

## Acceptance outcome

Sprint 5 is complete.

- framework ownership is determined by registration origin: factory-created services are ForgeMCP-owned while `provide(token, value)` remains caller-owned;
- `Symbol.asyncDispose` and `Symbol.dispose` are supported with async disposal preferred;
- application, execution-scoped, and transient factory results are disposed in reverse successful-construction order at their owning lifecycle boundaries;
- startup rollback cleans up application resources already constructed before a later failure;
- execution scopes clean up request-owned resources on success and failure;
- disposal is idempotent and best-effort, with deterministic service identities retained for cleanup failures;
- shutdown enters `Stopping`, rejects new executions, drains active executions, then disposes application-owned resources;
- application cleanup failures leave the application terminal in `Stopped`;
- the official MCP adapter validates sequential request cleanup, application cleanup, caller-owned values, and safe close during an in-flight tool call;
- `McpServer.close()` now waits for ForgeMCP application drain and cleanup before resolving;
- Sprint 5 acceptance is documented in README, architecture, roadmap, changelog, planning, and ADR-0008;
- repository CI, dependency security, CodeQL, coverage, and SonarQube Cloud Quality Gate are required for the acceptance PR.

## Explicit non-goals

- lifecycle inference from method names;
- `FinalizationRegistry` cleanup;
- arbitrary service `start()`/`stop()` hooks;
- health/readiness callbacks;
- retrying failed disposal hooks;
- cancellation/timeouts for executions;
- user-created child scopes;
- session/connection service lifetimes;
- automatic disposal of `provide(token, value)` instances.

# v0.3 Sprint 1 — Configuration Foundation

## Sprint goal

Give ForgeMCP applications a deterministic, testable configuration model that modules can consume without reading process-global state directly.

This sprint intentionally does **not** implement a full dependency-injection container. Configuration is the first production application concern for v0.3; dependency registration and scopes follow in later v0.3 sprints.

## User outcome

A developer can:

1. provide explicit configuration while building an application;
2. optionally layer environment-backed values;
3. consume configuration while composing a module;
4. fail startup with a clear error when required configuration is missing;
5. test modules with deterministic in-memory configuration.

## Design constraints

- configuration contracts belong in `@forgemcp/core`;
- Node/environment implementations belong in `@forgemcp/application`;
- core must not read `process.env`;
- configuration precedence must be deterministic and documented;
- missing required values must fail before tool execution;
- no global singleton configuration;
- no service locator;
- no decorator/reflection dependency;
- public behavior must have tests and maintain the repository coverage threshold.

## Planned vertical slice

```text
ForgeApplicationBuilder
        |
        +--> configuration values
        +--> environment source
        |
        v
 resolved Configuration
        |
        v
 Module.configure(...)
        |
        v
 module reads required values
        |
        v
 tool constructed with explicit dependencies
```

## Sprint backlog

### S1.1 Configuration contracts

Define the smallest useful protocol-neutral contracts and key/value semantics.

Acceptance:

- optional lookup;
- required lookup with deterministic error;
- immutable read surface;
- no Node-specific types in core.

### S1.2 Configuration composition

Allow application configuration sources to be registered and resolved in deterministic order.

Acceptance:

- later sources override earlier sources;
- application startup receives one resolved snapshot;
- source failures fail startup and preserve lifecycle guarantees.

### S1.3 Environment-backed source

Add a Node runtime source that maps environment variables into ForgeMCP configuration.

Acceptance:

- configurable prefix;
- deterministic key normalization;
- no mutation of `process.env`;
- injectable environment dictionary for tests.

### S1.4 Module consumption

Expose the resolved configuration to module composition without introducing global state.

Acceptance:

- a module can read configuration during `configure()`;
- existing modules that only register tools/middleware remain straightforward to migrate;
- configuration is not protocol-specific.

### S1.5 Tests, docs, and example

Prove the complete configuration flow.

Acceptance:

- unit tests for lookup, precedence, environment mapping, and errors;
- application lifecycle regression tests;
- README example;
- architecture documentation;
- CI, security, coverage, and Sonar gates green.

## Definition of done

Sprint 1 is complete only when a clean consumer example can configure an MCP-backed ForgeMCP application without importing `process.env` inside its module or tool and all repository quality gates pass.

## Explicit non-goals

The following remain outside Sprint 1:

- constructor injection;
- service lifetimes/scopes;
- module dependency graphs;
- lifecycle-aware services;
- secrets managers;
- remote configuration providers;
- configuration hot reload;
- decorators or reflection metadata.

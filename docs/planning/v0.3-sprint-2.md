# v0.3 Sprint 2 — Service Registration Foundation

**Status:** complete.

## Sprint goal

Give ForgeMCP applications an explicit, typed service-registration model so modules can construct tools and middleware from configured application dependencies without global state, decorators, reflection metadata, or hidden runtime service location.

Sprint 1 proved deterministic configuration. Sprint 2 uses that configuration as an input to service construction.

## User outcome

A developer can:

1. define a typed service token;
2. register an application service value or factory;
3. construct a service from configuration and other application services;
4. access resolved services while composing a module;
5. construct tools and middleware with explicit dependencies;
6. receive deterministic duplicate, missing, and circular-dependency failures;
7. verify the flow through the MCP adapter.

## Design constraints

- service contracts belong in `@forgemcp/core`;
- default service runtime belongs in `@forgemcp/application`;
- no Node-specific types in core;
- no global container;
- no decorators;
- no reflection metadata;
- no automatic constructor injection;
- no ambient service resolution during tool execution;
- service construction happens during application startup;
- failed construction must preserve lifecycle rollback;
- services use one application lifetime in this sprint;
- request/session/transient scopes are deferred;
- existing configuration behavior remains unchanged;
- existing module/tool/middleware APIs should remain source-compatible where practical;
- public behavior requires tests and must preserve repository quality gates.

## Lifetime decision for Sprint 2

Sprint 2 deliberately supports a single application lifetime: one successfully resolved service instance per application start.

This gives ForgeMCP a useful dependency-construction model without prematurely introducing request scopes, transient services, disposal graphs, or scope propagation.

Later v0.3 work can add lifetimes only after real use cases demonstrate the required semantics.

## Dependency-resolution rule

Factories may resolve previously registered or recursively resolvable services through the provider supplied to the factory.

The runtime must track the active resolution path. Resolving a token already present in that path is a circular dependency and must fail with a deterministic diagnostic that includes the cycle.

No partially resolved provider becomes visible to module composition.

## Definition of done

Sprint 2 is complete only when a clean consumer can:

```ts
const apiClient = createServiceToken<ApiClient>("apiClient");

const app = ForgeApplicationBuilder.create()
  .configure({
    "api.baseUrl": "https://example.test",
  })
  .provideFactory(apiClient, ({ configuration }) =>
    new ApiClient(configuration.require("api.baseUrl")),
  )
  .use(ApiModule)
  .build();

await app.start();
```

and `ApiModule` can construct a tool with the resolved `ApiClient`, expose it over MCP, and pass every repository quality gate.

This definition of done is satisfied by the Sprint 2 integration suite.

## Explicit non-goals

- request-scoped services;
- transient/scoped lifetimes;
- child scopes;
- module dependency graphs;
- automatic constructor injection;
- decorators/reflection;
- lifecycle-aware disposal;
- plugin-driven service discovery;
- runtime ambient service location.

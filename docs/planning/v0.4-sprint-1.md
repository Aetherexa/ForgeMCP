# v0.4 Sprint 1 — Observability Foundation and Execution Correlation

**Status:** planned.

## Sprint goal

Expose ForgeMCP runtime behavior through a provider-neutral diagnostic event stream that preserves execution correlation without coupling the framework to a logging vendor or telemetry SDK.

v0.4 is the Production Operations milestone. Structured logging, traces, metrics, health, and runtime diagnostics all need a stable source of lifecycle facts. Sprint 1 establishes that source.

## Existing correlation model

ForgeMCP already creates one immutable execution metadata record per `Application.execute()` invocation:

```ts
interface ExecutionMetadata {
  readonly id: string;
  readonly startedAt: Date;
  readonly attributes: Readonly<Dictionary<unknown>>;
}
```

The existing `execution.id` remains the canonical Forge execution correlation identity.

This sprint does not generate a second Forge request ID, trace ID, or correlation ID.

Transport-specific identifiers continue to live in execution attributes. The MCP adapter currently contributes:

- `mcp.requestId`;
- `mcp.sessionId` when available;
- `mcp.meta` when available.

Future trace/span identifiers may also be carried as diagnostic attributes, but they do not replace the Forge execution ID.

## Diagnostic model

The intended core contracts are equivalent to:

```ts
interface DiagnosticEvent {
  readonly name: string;
  readonly timestamp: Date;
  readonly attributes: Readonly<Dictionary<unknown>>;
  readonly execution?: ExecutionMetadata;
}

interface DiagnosticListener {
  onEvent(event: DiagnosticEvent): void;
}
```

Exact implementation details remain subject to the contract task, but the architecture requires:

- protocol-neutral contracts;
- synchronous listener invocation;
- immutable event snapshots;
- deterministic listener order;
- application-local registration;
- stable machine-readable event names.

## Why synchronous listeners

The framework should not own exporter queues, network retries, telemetry flushing, or background delivery in the foundation layer.

A synchronous listener can:

- write to a structured logger;
- start/end an OpenTelemetry span;
- increment a metrics SDK counter;
- enqueue an event into an external buffer;
- capture events during tests.

Actual exporters may operate asynchronously behind those libraries.

This prevents the framework from making tool latency depend on arbitrary telemetry network I/O.

## Registration model

Listeners are registered explicitly on the application builder.

The intended shape is equivalent to:

```ts
ForgeApplicationBuilder.create()
  .observe(listener)
  .use(MyModule)
  .build();
```

Properties:

- no process-global observer registry;
- one application owns its listener list;
- registration order is preserved;
- application instances remain isolated;
- listeners registered on one application never receive events from another.

The exact public method name is finalized in the contract task. `observe(...)` is the current preferred name because it describes consuming runtime diagnostics without implying a concrete logging backend.

## Event naming

Framework-owned event names use a stable dot-separated namespace.

Initial Sprint 1 events:

### Application lifecycle

- `application.starting`;
- `application.started`;
- `application.start.failed`;
- `application.stopping`;
- `application.stopped`;
- `application.stop.failed`.

### Execution lifecycle

- `execution.started`;
- `execution.completed`;
- `execution.failed`.

Later v0.4 slices may add structured-log, health, service, module, or telemetry-specific events, but existing event names should remain stable.

## Event payload boundary

Framework diagnostic events report runtime facts, not arbitrary application payloads.

The foundation must not automatically emit:

- tool input;
- tool result value;
- service values;
- configuration secrets;
- exception object serialization;
- arbitrary module state.

Execution lifecycle events may include framework-controlled attributes such as:

- tool name;
- duration;
- lifecycle state;
- failure classification;
- execution metadata.

The execution metadata object may contain application/transport attributes because those attributes already belong to the execution context. Built-in structured logging added later must not serialize arbitrary execution attributes by default without an explicit policy.

## Failure isolation

Diagnostics are observational.

A diagnostic listener failure must not:

- fail application startup;
- fail a successful tool call;
- replace a tool error;
- prevent service cleanup;
- prevent application shutdown;
- stop later listeners from receiving the same event.

Listener failures are therefore isolated and ignored by the primary operation in Sprint 1.

The runtime does not emit a second diagnostic event describing a listener failure because that can recurse indefinitely.

A later runtime-diagnostics slice may expose bounded listener-failure counters/snapshots without recursively using the same event stream.

## Application lifecycle ordering

Expected ordering for successful startup/shutdown:

```text
application.starting
application.started
...
application.stopping
application.stopped
```

Expected startup failure:

```text
application.starting
application.start.failed
```

The failure event is emitted after rollback cleanup attempts complete so the event reflects the externally visible operation outcome.

Expected stop failure:

```text
application.stopping
application.stop.failed
```

The application remains terminal in `Stopped` according to the existing lifecycle contract.

## Execution lifecycle ordering

Every valid `Application.execute()` invocation emits exactly one terminal execution event.

Successful execution:

```text
execution.started
execution.completed
```

Failed execution:

```text
execution.started
execution.failed
```

The same `ExecutionMetadata.id` is present for both events.

The terminal event is emitted only after execution-scope cleanup finishes because cleanup is part of the existing execution promise boundary.

Duration therefore measures the complete Forge execution boundary, including request-owned cleanup.

## Concurrency

Concurrent tool calls must remain independently correlated.

```text
execution.started  id=A
execution.started  id=B
execution.completed id=B
execution.completed id=A
```

Ordering is guaranteed only within one execution, not globally across concurrent executions.

Listeners must use `execution.id` rather than event order to correlate concurrent activity.

## MCP correlation

The MCP adapter continues to call:

```text
MCP request
   |
   +--> createMcpExecutionAttributes(...)
   |
   +--> Application.execute(...)
             |
             +--> Forge execution.id
             +--> mcp.requestId attribute
             +--> mcp.sessionId attribute (when available)
```

Forge-generated execution IDs remain unique for each MCP call.

No MCP SDK type enters the core diagnostic contracts.

## Relationship to later v0.4 slices

Sprint 1 provides the event source.

Later slices can consume it:

### Structured logging

Translate diagnostic events into structured log records with explicit level/category policy.

### Traces

Map execution lifecycle events to spans while retaining `execution.id` as a Forge correlation attribute.

### Metrics

Count starts/completions/failures and record durations without parsing logs.

### Health/runtime diagnostics

Expose bounded runtime state and diagnostic health without turning the event stream into a mutable global registry.

## Definition of done

Sprint 1 is complete when an application can explicitly observe deterministic runtime lifecycle events, correlate each execution using the existing Forge execution ID, retain protocol-specific correlation attributes, and do so without global state, telemetry SDK coupling, payload leakage by default, or listener failures changing application behavior.

## Explicit non-goals

- built-in console/file logger;
- OpenTelemetry SDK dependency;
- network exporter;
- spans or metrics implementation;
- health/readiness model;
- runtime diagnostic snapshot API;
- tracing-context propagation standards;
- sampling;
- log redaction policy;
- asynchronous listener contract;
- listener retry/queueing;
- raw tool input/result capture.

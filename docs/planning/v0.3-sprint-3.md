# v0.3 Sprint 3 — Dependency Lifetimes and Execution Scopes

**Status:** complete.

## Sprint goal

Extend ForgeMCP's explicit dependency model with deterministic application, execution-scoped, and transient lifetimes while preserving the framework's no-reflection, no-global-container architecture.

Sprint 2 proved application-lifetime service construction. Sprint 3 introduces shorter-lived dependencies only at a lifecycle boundary ForgeMCP already owns: one `Application.execute()` invocation.

## User outcome

A developer can:

1. keep existing application service registrations unchanged;
2. register execution-scoped and transient service factories explicitly;
3. receive one scoped instance per application execution;
4. resolve fresh transient instances inside an execution scope;
5. consume shorter-lived services through the execution context rather than process-global state;
6. safely mix application and shorter-lived dependencies under deterministic lifetime rules;
7. verify isolation through the official MCP adapter.

## Design constraints

- existing `provide(...)` and `provideFactory(...)` remain application-lifetime by default;
- application values remain application-lifetime;
- shorter-lived registrations are factory-based;
- one `Application.execute()` call owns one execution scope;
- overlapping executions own isolated scopes;
- application services may depend only on application services;
- execution-scoped services may depend on application, execution-scoped, and transient services;
- transient services may depend on application, execution-scoped, and transient services when resolved inside an execution scope;
- resolving a shorter-lived service from application/module composition must fail deterministically;
- async factories remain supported;
- circular and missing dependency diagnostics remain deterministic;
- no decorators, reflection metadata, automatic constructor injection, or process-global container;
- lifecycle-aware disposal hooks are deferred to a later v0.3 slice;
- existing tools that do not use scoped services remain source-compatible;
- public behavior requires automated tests and existing CI/security/Sonar gates.

## Lifetime dependency matrix

| Consumer lifetime | Application dependency | Execution dependency | Transient dependency |
| --- | --- | --- | --- |
| Application | allowed | rejected | rejected |
| Execution | allowed | allowed | allowed |
| Transient (inside scope) | allowed | allowed | allowed |

The application row deliberately rejects shorter-lived dependencies. Otherwise an application singleton could capture a scoped/transient instance and accidentally extend its lifetime.

## Scope rule

ForgeMCP does not introduce a process-global service locator.

Shorter-lived resolution is carried explicitly on the already request-local `ExecutionContext`. This keeps the scope tied to the execution pipeline and makes concurrency isolation observable and testable.

`ModuleBuilder.services` remains the synchronous application-lifetime provider. Modules cannot resolve execution-scoped or transient services while composing tools.

## Definition of done

Sprint 3 is complete when two concurrent MCP tool calls can share one application service while receiving isolated execution-scoped instances, transient resolution behaves as documented, lifetime violations fail deterministically, and all repository quality gates pass.

Acceptance evidence:

- ADR 0006 defines execution-owned scopes and lifetime safety;
- issues #36–#39 delivered architecture, runtime resolution, execution integration, and official MCP validation;
- application tests prove sequential/concurrent isolation and failure recovery;
- MCP integration tests prove application reuse, scoped isolation, transient freshness, and overlapping-call isolation through the official SDK path;
- CI, coverage, Dependency security, CodeQL, and SonarQube Cloud gates are required for the acceptance PR.

## Explicit non-goals

- session/connection lifetime;
- child scopes created directly by application code;
- lifecycle-aware disposal hooks;
- automatic constructor injection;
- decorators or reflection metadata;
- module dependency graphs;
- plugin-driven service discovery.

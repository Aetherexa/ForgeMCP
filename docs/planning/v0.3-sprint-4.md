# v0.3 Sprint 4 — Module Dependencies and Deterministic Composition

**Status:** planned.

## Sprint goal

Add an explicit, deterministic module dependency graph while preserving ForgeMCP's existing `.use(Module)` composition model and no-reflection architecture.

Sprint 3 completed service lifetimes and execution scopes. Sprint 4 addresses the next composition problem: modules selected by an application may require other selected modules to configure first.

## User outcome

A developer can:

1. keep existing modules with no dependencies unchanged;
2. declare required module dependencies explicitly on a module type;
3. select modules with `.use(...)` in any order;
4. rely on ForgeMCP to configure dependencies before dependents;
5. receive deterministic missing-dependency diagnostics;
6. receive deterministic circular-dependency paths;
7. retain registration order for otherwise independent modules;
8. verify dependency-aware composition through the official MCP adapter.

## Design constraints

- `.use(Module)` remains the only application-level module selection API;
- dependencies do not auto-register hidden modules;
- dependency metadata is declared statically on the module type;
- existing modules without dependency metadata remain source-compatible;
- module constructors remain no-argument;
- no decorators, reflection metadata, constructor inspection, or global module registry;
- graph validation completes before any module `configure(...)` call;
- dependencies configure before dependents;
- independent modules preserve `.use(...)` registration order;
- each selected module configures exactly once;
- diamond graphs are deduplicated by module constructor identity;
- missing dependencies identify both dependent and missing modules;
- circular dependencies report a deterministic path;
- dependency metadata does not expose module instances;
- module dependencies do not create a service locator or second DI container;
- optional/conditional dependencies are deferred;
- public behavior requires automated tests and existing CI/security/Sonar gates.

## Planned public shape

The intended core contract is an optional static dependency declaration on a module type:

```ts
import type {
  Module,
  ModuleBuilder,
  ModuleType,
} from "@forgemcp/core";

class DatabaseModule implements Module {
  configure(builder: ModuleBuilder): void {
    // contribute database-backed capabilities
  }
}

class OrdersModule implements Module {
  static readonly dependencies: readonly ModuleType[] = [DatabaseModule];

  configure(builder: ModuleBuilder): void {
    // safe to contribute after DatabaseModule has configured
  }
}
```

Application selection remains explicit:

```ts
ForgeApplicationBuilder.create()
  .use(OrdersModule)
  .use(DatabaseModule)
  .build();
```

Even though `OrdersModule` is registered first, the validated plan configures `DatabaseModule` before `OrdersModule`.

If `DatabaseModule` is not selected with `.use(DatabaseModule)`, startup fails rather than silently auto-registering it.

The exact type spelling may be refined during implementation without changing these semantics.

## Composition model

```text
ForgeApplicationBuilder
        |
        +--> use(ModuleA)
        +--> use(ModuleB)
        +--> use(ModuleC)
        |
        v
selected module set
        |
        +--> read explicit dependency metadata
        +--> validate required modules
        +--> detect dependency cycles
        +--> stable topological ordering
        |
        v
module composition plan
        |
        v
Module.configure(...)
        |
        +--> dependencies first
        +--> independent modules preserve selection order
        +--> each module exactly once
```

## Ordering rules

The module planner is stable.

Given selected modules in registration order:

```text
A, B, C
```

with `A -> C` meaning A depends on C, the planner produces:

```text
C, A, B
```

B remains after A because no graph edge requires B to move ahead of it.

For a diamond:

```text
    A
   / \
  B   C
   \ /
    D
```

D is configured once, before B and C; B and C are ordered according to their stable discovery/registration order; A is configured after both.

## Failure rules

### Missing dependency

A dependency declaration never selects a module implicitly.

If `OrdersModule` depends on `DatabaseModule` but only `OrdersModule` is selected, planning fails before module configuration begins.

The diagnostic identifies:

- dependent module;
- missing dependency.

### Circular dependency

A cycle such as:

```text
A -> B -> C -> A
```

fails before configuration begins.

The diagnostic retains a deterministic module path:

```text
A -> B -> C -> A
```

### Startup rollback

Graph planning happens before any module instance is configured.

A graph validation failure therefore leaves no partially configured module contributions. `ForgeApplication.start()` returns to `Created` under the same startup retry semantics used by configuration and service failures.

## Definition of done

Sprint 4 is complete when a dependency-aware application can select modules in arbitrary order, configure a stable validated graph exactly once, fail deterministically for missing/circular relationships before partial composition, expose the resulting application through the official MCP adapter, and pass every repository quality gate.

## Explicit non-goals

- automatic dependency registration;
- optional module dependencies;
- conditional/configuration-driven module dependencies;
- module instance lookup;
- constructor injection;
- decorators or reflection metadata;
- module-scoped dependency containers;
- runtime module loading/unloading;
- plugin discovery.

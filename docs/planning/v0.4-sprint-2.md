# v0.4 Sprint 2 — Structured Logging

**Status:** implementation complete; final acceptance gates tracked in #87.

## Sprint goal

Turn the provider-neutral diagnostic event stream from Sprint 1 into safe, deterministic structured log records without introducing logging-vendor coupling or duplicating runtime lifecycle instrumentation.

## Architecture

Runtime diagnostic events remain the only lifecycle source. A structured logging listener consumes those events, maps them to stable log levels/messages, projects safe attributes, and forwards immutable records to a provider-neutral sink.

Flow:

    ForgeApplication
      -> DiagnosticEvent
      -> StructuredLogListener
      -> StructuredLogSink

## Provider-neutral model

The intended contracts are:

    type LogLevel = "debug" | "info" | "warn" | "error";

    interface StructuredLogRecord {
      readonly timestamp: Date;
      readonly level: LogLevel;
      readonly event: DiagnosticEventName;
      readonly message: string;
      readonly executionId?: string;
      readonly attributes: Readonly<Dictionary<unknown>>;
    }

    interface StructuredLogSink {
      write(record: StructuredLogRecord): void;
    }

Exact names may be refined by the contract task, but this behavior is normative.

## Event-to-level mapping

- application.starting -> info
- application.started -> info
- application.start.failed -> error
- application.stopping -> info
- application.stopped -> info
- application.stop.failed -> error
- execution.started -> info
- execution.completed -> info
- execution.failed -> error

Sprint 2 does not introduce dynamic level overrides.

## Correlation

ExecutionMetadata.id remains the canonical Forge correlation identity and is exposed as executionId on execution log records.

Transport identifiers such as MCP request/session IDs supplement that identity only when explicitly selected.

## Privacy boundary

Framework diagnostic attributes such as tool.name and duration.ms may be included by default.

Arbitrary ExecutionMetadata.attributes are excluded by default because they may contain sensitive or high-cardinality application/transport data.

Applications can explicitly allow selected execution attributes, for example mcp.requestId and mcp.sessionId. No wildcard include-all option is provided in this sprint.

Raw tool inputs/results, service values, configuration values, arbitrary module state, and exception serialization remain excluded by default.

## Immutability

Each structured log record is an immutable snapshot. Projected attributes are copied into a new frozen object and the record is frozen.

Deep-freezing arbitrary nested allowlisted values is not required.

## Sink boundary

The sink is synchronous. A sink may hand off to a provider SDK or caller-owned buffer, but ForgeMCP does not own exporter queues, retries, batching, backpressure, file rotation, or provider shutdown.

## Failure semantics

Structured logging is observational. Mapping, sink, serialization, and write failures must not change startup, tool execution, service cleanup, or shutdown behavior. Sprint 1 listener isolation remains the outer safety boundary.

## Stdio safety

MCP stdio reserves stdout for protocol framing. The built-in JSON Lines sink therefore writes to stderr only and never stdout.

Each record is encoded as one JSON object followed by a newline. Timestamps are serialized as ISO-8601 strings.

## MCP validation

The official MCP path must prove:

1. real calls produce correlated execution log records;
2. start/terminal records share one Forge executionId;
3. concurrent calls remain independently correlated;
4. MCP request/session IDs appear only when explicitly selected;
5. arbitrary MCP metadata and raw tool payloads are absent by default;
6. logging never writes to protocol stdout.

## Definition of done

Sprint 2 is complete when ForgeMCP converts its existing diagnostic stream into deterministic provider-neutral structured records, preserves canonical execution correlation, keeps arbitrary execution metadata private by default, provides a stdio-safe stderr JSON Lines sink, validates the behavior through the official MCP path, and passes all quality/security gates.

## Explicit non-goals

- Pino/Winston/Bunyan dependency;
- OpenTelemetry Logs SDK;
- network exporters;
- log file rotation;
- sampling;
- dynamic log-level reconfiguration;
- wildcard execution-attribute serialization;
- raw input/result logging;
- automatic exception serialization;
- asynchronous sink contract;
- sink retry/queueing/backpressure;
- process-global logger.
